- **System design (November 2026):** six senior/staff-level rounds with the owner's well-known titles: Design Twitter: the celebrity problem (`design-twitter`), Design Google Calendar (`design-calendar`, same id as the earlier calendar session so saved answers carry over), Design a Job Scheduler, Design DoorDash, Design a Distributed Queue (Kafka-like), Design Amazon E-commerce. They're based on the owner's interview notes, rewritten; never copy names, prices or anything private from those notes. `check.js` requires `board: true` on every system design session.
- **Behavioral:** Leadership & influence; Ownership, failure & impact; Collaboration, feedback & growth (hard feedback, a difficult teammate or stakeholder, changing your mind with data, why this role and where you want to grow). Visitors answer against a 45-minute timer, type or dictate (Web Speech API: Chrome, Edge, Safari; the button stays on through tab switches and silences until they press Stop), code in a CodeMirror editor with a language picker (Python, Java, C++, JavaScript, TypeScript, Go, C#), and draw on an Excalidraw whiteboard in design sessions. Everything autosaves in the visitor's browser (`localStorage`, keys `ct-practice:*`); nothing leaves the browser until they press "Send for review".
- Source: `_practice/sessions.js` (sessions), `_practice/problems.js` (runnable questions), `_practice/practice.js` (app), `_practice/practice.css`, plus the test runner files below. `ruby _blog/build.rb` builds `practice/` with the shared header (Practice marked current), footer, analytics snippet and cache-busting `?v=` on its files. Don't edit `practice/` by hand.
- Add or change a session: edit `_practice/sessions.js` (track, title, blurb, blocks with `min` and prompts; `kind: "code"` for the code editor, `board: true` for the whiteboard, `given` for code shown to the candidate). Blocks must add up to 45 minutes: `node _practice/check.js` (the build runs it too).
- **Coding practice sets (November 2026):** each set is two questions in 45 minutes: per question, clarify & plan (3 min), code (15 or 16), test & complexity (4). The sets are built at the end of `sessions.js` by `codingSet()` from the question data in `problems.js` (statement, input/output, constraints, sample tests that double as the examples, "what interviewers look for" for each block, a follow-up, and the signature: `fn` + `params`/`returns` types, or `cls` + hand-written `starters` for a class question). Starter code for all 7 languages is generated from the signature (snake_case in Python, PascalCase in C#). Sample tests are original or the owner's (inputs that matched well-known public examples were replaced in November 2026). The 20 questions: S1 unpaired number (XOR), unpaired in a sorted list (O(log n)); S2 backspace keys, fewest removals to balance brackets (any valid answer accepted by the `parens` checker); S3 fence posts with ≥ k coats (sweep), fewest arrows (the owner's first example is a sample; his touching example, which matches a well-known public example, is a hidden test instead); S4 sliding window maximum, longest ones with k flips; S5 search a row/column-sorted grid, smallest water tank (binary search on the answer); S6 paint houses, sums with limited copies (distinct values, mod 10⁹+7); S7 cycle in a directed graph, fewest semesters (Kahn levels, −1 on a cycle); S8 check a sudoku, move to the ends (owner's examples verified by BFS: answer = n − longest run of a that appears in order in b); S9 Scoreboard class (tests are operation sequences), k largest from a heap; S10 subarrays summing to k (divisible-by-k as follow-up), younger/older halves (two heaps; equal ages: earlier arrival counts as younger); S11 no dead ends in a BST (a leaf is a dead end when its value v is squeezed between v − 1 and v + 1 by its ancestors, with 0 as the floor), count a complete tree in O(log² n); S12 days until a strictly warmer day (monotonic stack), fair candies (two passes); S13 palindrome within k deletions (O(n²) DP, n ≤ 200 so memoized recursion stays well under the browser limit), next arrangement in place (wraps around); S14 distance to the nearest exit (walls −1, exits 0, rooms 2147483647; multi-source BFS), gentlest path (minimum of the maximum step; Dijkstra or binary search); S15 tasks with a cooldown (counting formula), heater range (sort + binary search).
- **Tree inputs:** a question parameter of type `tree` is written in level order with null (None in Python) for a missing child, e.g. `[10, 8, 15, null, 9]`, and shows that way in examples and results. Both runners build `TreeNode` objects (`val`, `left`, `right`; `TreeNode` is also available to the candidate's code) before calling the function, and the starter code for every language opens with a comment describing `TreeNode`. A full-size test can pass `{"$complete": n}` instead: a complete tree whose nodes are made only when visited (children are held through weak references and the size is out of reach of the candidate code), which is how S11b checks O(log² n) on a tree of over a billion nodes. `inplace: <index>` in a question lets the candidate change that list in place and return nothing (S13b, S14a).
- **Run / Submit:** Run checks the sample tests (input, expected, your output, printed output, errors with line numbers); Submit adds the hidden tests (only counts and the first failing hidden test's number and kind are shown, never its input or expected value). Code runs in the browser, no server. JavaScript: a fresh Web Worker per run (`_practice/runner-js.js`). Python: Pyodide 0.26.4 (`_practice/runner-py.js` + `_practice/harness.py`) from jsDelivr (`cdn.jsdelivr.net/pyodide/v0.26.4/full/`, then the npm mirror; about 10 MB the first time, then cached), and **every Python run gets a fresh interpreter in a new worker**, so nothing a run changes (patched modules, recursion limit) reaches the next; the next worker loads in the background after each run (and when someone focuses a runnable editor in Python), and Python runs go one at a time through a queue ("Queued…", "Restarting Python…"). Deep Python recursion can overflow the browser stack before Python's own limit (memoized recursion with `@cache`/`@lru_cache` failed after about 400–450 levels in Chrome, November 2026; plain recursion is fine up to the 3000 limit): the worker catches that fatal error and reports "Recursion too deep for Python in the browser…", leaving the remaining tests not run, so keep inputs where recursion depth matters well under ~400. Each run carries a random nonce kept out of reach of the candidate's code, and result messages without it are ignored (so code can't post fake passes), and the harness keeps its own references to json, io and sys. A test running over 5 s is stopped by terminating the worker ("took longer than 5 s or used too much memory"). Answers are saved before every run and results right after, because runaway JavaScript memory can still make the browser close the tab. Ctrl/Cmd+Enter runs, Shift+Ctrl/Cmd+Enter submits. Java, C++, Go, C# and TypeScript can be written but not run: Run/Submit and results are hidden and one line explains this (owner's decision, November 2026). Results are saved per question **and language** (`runs`), restored when switching back, and included in the downloaded/sent answers ("Tests (Python): …", or "not run"). Comparators live in `_practice/judge.js` (shared by the page and the verify script): exact, unordered, float, or a named checker; `keep` in a question makes both runners fail a function that changes that argument (S9b's heap).
- **Speed:** questions with `speed: true` (S3 both, S4 both, S5 tank, S9 Scoreboard, S10 both, S11 complete-tree count, S12 both, S13 k-palindrome, S14 both, S15 heaters) add 1–2 full-size hidden tests at the constraint limits. Their inputs are generated on Submit from a seed by the generators in `judge.js` (the same code makes them for `generate.py` through Node), and only the SHA-256 of the expected output's JSON ships. Timed: the references take under 0.9 s each in Pyodide on a desktop (0.6 s in CPython), and the naive approaches named in the statements (in `_practice/tests/naive/`) fail or run past the 5 s limit. The other questions say on the page that their hidden tests check correctness on edge cases and medium inputs, not speed (S1b's O(log n), S9b's O(k log k) and S6b's sliding sum can't be told apart from simpler approaches at these sizes; S11a, S13b and S15a have no meaningfully slower common approach). For S11–S15 the references take under 0.7 s each in Pyodide.
- **Hidden tests are not secret.** The site is static, so they ship to the browser: `practice/hidden/<id>.txt` is base64 JSON (seeds and hashes for the full-size ones), fetched only on Submit. Anyone can decode them (and the repository is public); the encoding only keeps them out of plain sight.
- **Add a coding question:** add it to `_practice/problems.js`; write a reference solution as a candidate would in `_practice/tests/ref/<id>.py` and `<id>.js`; add a brute force and a test generator to `_practice/tests/generate.py` (fixed seed, edge cases plus medium cases); if speed matters, add a seeded generator to `GENS` in `_practice/judge.js`, sizes to `FULL` in `generate.py`, a naive solution in `_practice/tests/naive/`, and `speed: true`; run `python3 _practice/tests/generate.py` (writes `_practice/tests/hidden/<id>.json`, checking every case against the brute force); use the question in a `codingSet(...)` in `sessions.js`; run `node _practice/tests/verify.js --speed` and `ruby _blog/build.rb`.
- **Verify:** `node _practice/tests/verify.js` runs `check.js`, checks the hidden tests are up to date and agree with the brute forces, then runs every Python reference through `harness.py` (as in Pyodide) and every JavaScript reference through `runner-js.js`, judged by `judge.js`: 579 tests (all 36 questions), all must pass in both languages, plus the AI-round checks above. The JavaScript references get a deep copy of each input, as the browser does, because in-place answers change their input. Add `--speed` to also time the full-size tests (references under 1.5 s; naive solutions must fail or exceed 5 s). Reference and naive solutions stay out of the shipped site (`_practice/` isn't published).
- **AI coding rounds (November 2026):** a separate group after the coding sets, ids `ai-round-1` … `ai-round-6`, 45 minutes each: 1 catch the AI's bug (leaderboard ranks with ties), 2 extend existing code (an `Inventory` class gains expiring reservations with an injected clock), 3 debug with AI (a log summary with three bugs), 4 tests first (write tests for a sliding-window rate limiter, "Check my tests" runs them against a correct version and five buggy ones and reports "caught 4/5", then implement it), 5 refactor under constraints (slow, messy visit-session counter; speed-tested), 6 make it resilient (retries with capped exponential backoff and full jitter, attempt limit, overall deadline, no retry on non-retryable errors, tested with a fake service, clock and rand). Problems live in `_practice/ai-problems.js` (same format as `problems.js`, plus the given code in Python and JavaScript as `starters`, shown read-only in the problem and pre-filled; other languages get a short note) and `AI_ROUNDS` there; `sessions.js` builds the rounds (clarify & plan 5 min, work with the AI 30, verify & explain 10; round 4: 5 + write tests first 10 + implement 20 + verify 10).
